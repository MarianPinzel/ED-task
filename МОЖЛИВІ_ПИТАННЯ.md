# Можливі питання по завданню — і відповіді

Підготовка до захисту. Питання згруповані по темах, відповіді короткі й
конкретні, з посиланнями на реальний код.

## 1. Загальна концепція

**Q: Чому AWS Secrets Manager, а не просто змінні середовища / .env файл?**
A: Env-файли і змінні середовища зберігаються у відкритому вигляді на диску
чи в конфігурації процесу — будь-хто з доступом до сервера чи до repo їх
бачить. Secrets Manager: шифрує значення at rest, контролює доступ через
IAM (не просто "хто має SSH"), логує кожен звернення в CloudTrail, і
дозволяє ротацію без передеплою коду.

**Q: Чим Secrets Manager відрізняється від Parameter Store (SSM)?**
A: Parameter Store (SecureString) теж шифрує значення, дешевший, але не
має вбудованої ротації, версіонування слабше і немає нативної інтеграції з
RDS для авто-ротації пароля. Secrets Manager платний за секрет/місяць, але
робить ротацію "з коробки" через Lambda.

**Q: Які типи секретів ти керуєш і чому саме ці три?**
A: Пароль БД (`random_password`, повністю авто-генерований), API-ключ
(значення ззовні, як JSON-обʼєкт), SSH deploy-ключ (значення ззовні, PEM).
Обрано навмисно різні: один Terraform генерує сам, два — приходять від
оператора, і вони по-різному ротуються (див. п.5).

## 2. Шифрування / KMS

**Q: Що таке CMK і чим відрізняється від дефолтного ключа AWS?**
A: CMK (Customer Managed Key) — ключ, яким керуєш ти (можеш дивитись,
обмежувати доступ, ротувати, видаляти), на відміну від
`aws/secretsmanager` — спільного ключа AWS, над яким контролю майже
немає. Код: [main.tf:74-79](main.tf#L74-L79).

**Q: Навіщо `enable_key_rotation = true`?**
A: AWS сам щорічно генерує новий backend key material для цього CMK;
старі версії лишаються, щоб розшифрувати вже зашифровані раніше дані.
Задовольняє вимогу "encryption best practices" з нефункціональних вимог
завдання.

**Q: Що таке `kms:ViaService` умова в IAM policy?**
A: Обмежує дозвіл `kms:Decrypt` так, щоб роль могла розшифровувати цим
ключем лише коли запит іде **через Secrets Manager**, а не напряму до KMS
API. Тобто навіть маючи дозвіл на Decrypt, роль не може використати цей
ключ довільно для розшифрування будь-чого. Код:
[main.tf:114-124](main.tf#L114-L124) (те, що ти виділив).

**Q: Що буде, якщо видалити KMS-ключ?**
A: `deletion_window_in_days = 7` — ключ не видаляється миттєво, є 7-денне
вікно очікування (можна скасувати видалення). Якщо ключ реально видалити —
всі секрети, зашифровані ним, стають нечитабельними назавжди (це навмисний
захист AWS від випадкового видалення).

## 3. IAM / Least Privilege

**Q: Як конкретно реалізовано least privilege тут?**
A: Політика `secrets_read_only` ([main.tf:102-125](main.tf#L102-L125))
дає рівно 2 дозволи: `secretsmanager:GetSecretValue` на 3 конкретні ARN
(не wildcard), і `kms:Decrypt` на 1 конкретний ключ з умовою ViaService.
Жодних `Put*`, `List*`, `Delete*`, доступу до інших сервісів.

**Q: Хто/що може assume-нути цю роль?**
A: Тільки сервіс `ec2.amazonaws.com` (trust policy,
[main.tf:86-94](main.tf#L86-L94)) — жодна людина не може напряму
"стати" цією роллю, лише сам EC2 як сервіс, і лише той конкретний
інстанс, якому призначено instance profile.

**Q: Як ти довів, що least privilege реально працює, а не просто написаний в коді?**
A: Живий доказ: коли на інстансі підняли SSM-агент, він спробував
викликати `ssm:UpdateInstanceInformation` і отримав `AccessDeniedException`
— тому що роль справді не має цього дозволу. Зафіксовано в
[artifacts/instance_secrets_retrieval_log.txt](artifacts/instance_secrets_retrieval_log.txt).

**Q: SSH-доступ оператора (твій ключ) — це те саме, що доступ застосунку?**
A: Ні, навмисно розділено. `aws_key_pair.operator` — це просто ключ для
входу людини на сервер (SSH логін), не має жодного стосунку до IAM-ролі чи
до секрету `ssh_deploy_private_key`, який зберігається в Secrets Manager
як окреме значення для застосунку/деплою.

## 4. Отримання секретів на інстансі

**Q: Як секрет потрапляє на сервер і чому це безпечно?**
A: `user_data.sh.tftpl` виконується один раз при завантаженні. Для
кожного секрету: `aws secretsmanager get-secret-value ... --output text >
файл` — значення одразу редиректиться у файл, ніколи не потрапляє у
змінну, яку можна було б випадково echo'нути. Права файлу виставляються
одразу (`chmod 600`/`400`), власник — службовий юзер `app` без логіну
(`/usr/sbin/nologin`).

**Q: Чому в journalctl нічого не видно, крім "success"?**
A: Скрипт явно логує лише факт: `logger "secrets-demo: retrieved X
successfully"` — сам код ніколи не передає значення секрету в `logger`,
`echo` чи будь-яку команду виводу. `set -euo pipefail` на початку скрипта
означає, що будь-яка помилка одразу зупиняє виконання — не буде
"мовчазного" продовження з порожнім/неповним секретом.

**Q: Чи Terraform колись бачить/показує значення секретів?**
A: Значення проходять через Terraform (variables → resource), але
`variables.tf` позначає їх `sensitive = true`, тому в `plan`/`apply`
виводі вони замінені на `(sensitive value)`. У `outputs.tf`
`db_password_value` теж `sensitive = true`. Але! Значення **зберігаються
у відкритому вигляді в `terraform.tfstate`** (файл стану) — це відома
властивість Terraform, тому state-файл теж треба захищати (не в git,
обмежений доступ, в проді — remote backend типу S3 з шифруванням +
обмеженим IAM).

## 5. Ротація

**Q: Як ротувати кожен із трьох секретів?**
A:
- `db_password` — повністю Terraform-керований: `terraform taint
  random_password.db_password && terraform apply` генерує нове випадкове
  значення.
- `api_key` / `ssh_key` — мають `lifecycle { ignore_changes =
  [secret_string] }` ([main.tf:52-54](main.tf#L52-L54),
  [69-71](main.tf#L69-L71)), тому ротуються ЗОВНІ Terraform:
  `aws secretsmanager put-secret-value --secret-id ... --secret-string
  ...`, і наступний `terraform apply` НЕ відкотить це значення назад.

**Q: Навіщо `ignore_changes`, якщо можна просто оновити значення в tfvars?**
A: Бо ці два секрети думаються як такі, що можуть ротуватись автоматично
(наприклад Lambda-ротацією або зовнішнім security-процесом) незалежно від
циклу деплою інфраструктури. Без `ignore_changes` наступний `apply`
перезаписав би нове значення старим, яке лежить у tfvars/state.

**Q: Чи є в тебе автоматична (Lambda-based) ротація?**
A: Ні, навмисно не робили — `enable_key_rotation` стосується лише
ротації KMS-ключа шифрування, а не значень секретів. Автоматична
ротація значень (`aws_secretsmanager_secret_rotation` + Lambda) не
входила в обов'язкові критерії ("can be rotated" виконується й ручним
шляхом), і для db-пароля чи фейкового API немає реальної системи, яку
Lambda мала б повідомити про новий пароль.

**Q: Сервер підхопить нове значення секрету автоматично після ротації?**
A: Ні — секрет читається лише один раз, при завантаженні (`user_data`
виконується тільки на first boot). Щоб підхопити нове значення, потрібно
або перестворити інстанс (`terraform apply -replace=aws_instance.app`),
або мати на сервері окремий процес/крон, який періодично сам перечитує
Secrets Manager (тут для демо-стенду цього немає).

## 6. Git-гігієна / стан репозиторію

**Q: Як ти гарантуєш, що секрет не потрапить в git?**
A: `.gitignore` виключає `terraform.tfvars` (єдине місце з реальними
значеннями), `*.tfstate`, `.terraform/`, `*.pem`, `*.key` — ще до першого
коміту. Перевірка постфактум:
```
git log -p --all | grep -iE "password|api_key|BEGIN (RSA|OPENSSH) PRIVATE KEY"
```
має повертати порожньо.

**Q: А що як секрет випадково закомітили і потім видалили файл?**
A: Видалення файлу новим комітом не прибирає його зі старих комітів — він
лишається в git-історії назавжди, поки не переписати історію
(`git filter-repo`/BFG) і форс-пушнути. Тому найкраще — не допустити
цього взагалі через `.gitignore` заздалегідь (що й зроблено).

## 7. Мережа / архітектура

**Q: Чому SSH дозволено лише з однієї IP (`operator_cidr`)?**
A: Security group ([main.tf:179-200](main.tf#L179-L200)) обмежує вхідний
22-й порт конкретним `/32` — принцип найменших привілеїв застосовано і на
мережевому рівні, не тільки на IAM.

**Q: Чому Ubuntu 24.04, а не Amazon Linux?**
A: Вимога завдання — навмисно взяли не "коробкове" рішення з готовим AWS
CLI (як в Amazon Linux 2023), а дистрибутив, де CLI треба ставити самим —
щоб показати весь процес bootstrap явно.

## 8. Труднощі, з якими зіткнулись (гарна тема для "розкажи про проблеми")

1. **AMI спочатку був Amazon Linux 2023 замість Ubuntu 24.04** —
   невідповідність вимозі, знайшли й переробили на офіційний Canonical AMI
   (owner `099720109477`).
2. **`apt-get install awscli` падав** — `E: Package 'awscli' has no
   installation candidate`. Виявилось, що Ubuntu 24.04 (Noble) прибрав
   цей пакет з архіву. Виправили на офіційний AWS CLI v2 installer
   (curl + unzip + `/tmp/aws/install`) — це до речі й офіційно
   рекомендований AWS спосіб, не залежить від пакетного менеджера
   дистрибутиву.
3. **Не було жодного SSH-ключа для входу на інстанс** — `aws_instance` не
   мав `key_name`. Додали окремий `aws_key_pair.operator`, явно відділений
   від секретного `ssh_deploy_private_key`.
4. Обидва баги виявили і виправили через реальний деплой + SSH-перевірку
   логів — не тільки `terraform plan`, а й живе тестування на інстансі.

## 9. Що можна покращити (якщо запитають "а що б ти зробив інакше в проді")

- Remote backend для `terraform.tfstate` (S3 + DynamoDB lock), із
  шифруванням і обмеженим IAM-доступом до бакету — зараз стан лежить
  локально у відкритому вигляді.
- Автоматична Lambda-ротація для db-пароля через нативну RDS-інтеграцію
  Secrets Manager (тут немає реальної RDS, тому не було сенсу).
- Секрет-специфічні KMS grants замість одного спільного CMK на всі три —
  для ще суворішої ізоляції між типами секретів.
- CloudTrail data events для Secrets Manager увімкнути явно (зараз
  покладаємось на дефолтне логування — для продакшн-аудиту варто
  розглянути окремий trail з детальнішими правилами).
- Egress-обмеження security group (зараз `0.0.0.0/0` на весь вихідний
  трафік) — можна звузити до конкретних AWS API-ендпоінтів через VPC
  endpoints.
