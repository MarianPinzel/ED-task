# Пояснення проєкту (для себе, не для здачі)

Цей файл — не частина офіційної здачі завдання (те, що вимагають — в
[README.md](README.md) англійською). Тут просто по-людськи розписано, що
тут взагалі відбувається, навіщо кожен шматок і що з цим робити далі.

## Що це за завдання взагалі

Тема: **навчитись безпечно керувати секретами (паролі, ключі) в
автоматизованому розгортанні інфраструктури**, замість того щоб хардкодити
їх у коді чи комітити в git.

Обраний інструмент: **AWS Secrets Manager** (сховище секретів від Amazon) +
**Terraform** (інструмент, який описує інфраструктуру кодом і сам її
створює/змінює в AWS).

## Що конкретно робить цей код

Уяви просту схему: тобі треба підняти сервер, якому потрібні пароль від
бази даних, ключ від стороннього API і SSH-ключ для деплою. Погана
практика — вписати ці значення прямо в код. Хороша практика — те, що тут
зроблено:

1. **Секрети створюються і шифруються в AWS Secrets Manager**, не в коді.
2. **Окремий ключ шифрування (KMS)** — не дефолтний від Amazon, а свій,
   з автоматичною щорічною ротацією.
3. **Сервер (EC2-інстанс)** отримує не самі секрети, а лише **дозвіл**
   (IAM-роль) читати рівно ці 3 секрети — і більше нічого.
4. При старті сервера **скрипт сам іде і забирає** значення секретів з
   Secrets Manager через `aws` CLI — і ніде їх не показує, не логує, не
   виводить на екран.
5. Секрети можна **замінити (ротувати)** окремо, без переписування
   Terraform-коду.

## Що є в кожному файлі — по-простому

- **[main.tf](main.tf)** — головний файл. Тут описано ВСЕ: мережа (VPC),
  правило файрвола (security group, пускає SSH тільки з твоєї IP), ключ
  шифрування (KMS), самі 3 секрети, права доступу (IAM), і сам сервер
  (EC2).
- **[variables.tf](variables.tf)** — "вхідні параметри". Те, що можна
  міняти без правки основного коду: регіон, назва проєкту, і власне самі
  секретні значення (позначені `sensitive = true`, щоб Terraform ніде їх
  не показував).
- **[outputs.tf](outputs.tf)** — що показати після завершення. ARN-и
  (адреси) секретів — можна, це не секретно. Самі значення секретів —
  заховані.
- **[user_data.sh.tftpl](user_data.sh.tftpl)** — bash-скрипт, який
  виконується на сервері один раз, при першому включенні. Він:
  - ставить AWS CLI
  - забирає 3 секрети з Secrets Manager у файли з обмеженими правами
    (600/400 — тільки власник файлу може читати)
  - пише в системний журнал тільки "секрет отримано успішно", без самого
    значення
- **[terraform.tfvars](terraform.tfvars)** — тут лежать РЕАЛЬНІ значення
  (твоя IP, тестовий API-ключ, SSH-ключ). Цей файл **ніколи не йде в
  git** (див. `.gitignore`).
- **[terraform.tfvars.example](terraform.tfvars.example)** — шаблон того
  самого файлу, але без реальних значень — просто приклад для інших.
- **[.gitignore](.gitignore)** — список файлів, які git повинен
  ігнорувати (tfvars, стан Terraform, ключі) — щоб секрети фізично не
  могли потрапити в репозиторій.
- **[README.md](README.md)** — офіційна документація для здачі: як це
  працює, як додати новий секрет, як ротувати.

## Що вже реально зроблено в AWS (не просто код, а по факту створено)

Твій акаунт: `263314209222` (юзер `vafla`), регіон **eu-central-1
(Frankfurt)** — важливо: не us-east-1, консоль треба перемкнути на
Frankfurt, щоб побачити.

Створено і працює:
- **VPC + підмережа + інтернет-шлюз** — мінімальна мережа для тестового
  сервера
- **Security Group** — пускає SSH тільки з твоєї IP
- **KMS-ключ** — `alias/secrets-demo-dev-secrets`, з ротацією
- **3 секрети в Secrets Manager**:
  - `secrets-demo/dev/db/password` — пароль (згенерований автоматично,
    випадковий)
  - `secrets-demo/dev/api/external-key` — тестовий API-ключ
  - `secrets-demo/dev/ssh/deploy-key` — тестовий SSH-ключ (для
    демонстрації, не для входу на сервер)
- **IAM-роль** `secrets-demo-dev-app-role` — має доступ ЛИШЕ на читання
  цих 3 секретів, нічого більше
- **EC2-сервер** (Ubuntu 24.04), зараз працює, публічна IP
  `63.177.237.26`

## Як я це перевірив, що воно реально працює

Я підключився по SSH до сервера (окремим ключем, який згенерував саме
для цього — не плутати з тим SSH-ключем, що зберігається як секрет) і
подивився:

1. `cloud-init status` → `done` — сервер повністю завантажився без
   помилок
2. Файли секретів на диску — є, з правильними правами (600/400), належать
   спеціальному службовому користувачу `app`
3. Системний журнал (`journalctl`) — показує тільки "retrieved
   db_password successfully" і подібне, **жодного реального значення
   секрету ніде не видно**
4. Бонус: коли AWS-агент (SSM) спробував зробити щось поза дозволеним
   колом прав, отримав відмову доступу — це доказ, що права дійсно
   обмежені (least privilege), а не просто "написано в коді, але
   насправді все дозволено"

Логи цієї перевірки збережені в [artifacts/](artifacts/):
- `terraform_apply_output.log` — вивід команди, яка все створила
- `instance_secrets_retrieval_log.txt` — логи з самого сервера

